# Crossplane-managed cluster lifecycle (brainstorm / plan)

Status: **idea, no code**. Nothing here is verified against the live cluster; items marked
**VERIFY** are things I believe but have not checked.

## Decisions so far (rev 2)

- **D1** The per-cluster age key is generated by the bootstrap step and stored on the manager (Secret). See Platform layer for the one remaining gap (secrets encrypted before the key exists).
- **D2** IPs and VM IDs are allocated **before** the `TalosCluster` is created (allocation docs updated by hand/script in the same commit). The composition never allocates; it only derives VM ID from IP.
- **D3** Worker count may go **0 -> N** but **never N -> 0** (enforced in the XRD, see Scaling).
- **D4** Talos VMs are **not** built with `terraform/modules/linux-vm`. They are cloned from Proxmox template **9100**. (Template 9100 was imported by hand and is not scripted or documented anywhere; the existing `talos-01` VM was created manually from it. Making it reproducible is phase 0 below.)
- **D5** Proxmox host settings (cluster node, storage pool, bridge, template) live in a separate, reusable environment object, not in each cluster. See "Proxmox environment".

## Goal

Add a new Kubernetes cluster with **one commit**:

1. VMs are created to the homelab standards (VLAN 10, IP/VM-ID rules, cloud-init/guest-agent, tags).
2. Talos is installed and bootstrapped.
3. The platform layer (Flux Operator + this repo's apps) comes up on it.

Hard requirements:

- **R1** The existing path (`hack/new-cluster.sh` -> `render.py` -> `bootstrap/bootstrap.sh`) keeps working,
  for clusters not built by Crossplane (kubeadm, hand-built Talos, the manager itself).
- **R2** Topology is `1 control plane + N workers`, `N >= 0`.
  - `N > 0`: normal scheduling (control plane tainted, MetalLB excludes it).
  - `N == 0`: workloads allowed on the control plane **and** MetalLB must announce from it.
- **R3** The existing `talos-test` cluster acts as the **manager** (runs Crossplane).

## Architecture

```
git commit ──> manager Flux ──> TalosCluster (XR) ──> Composition (pipeline)
                                   │
        ┌──────────────────────────┼──────────────────────────────┐
        ▼                          ▼                              ▼
   VM layer                   Talos layer                  Platform layer
 (Proxmox VMs from         (secrets bundle, machine      (kubeconfig -> bootstrap.sh
  Talos image, IPs,         configs, apply, bootstrap     logic: Flux Operator, age key,
  IDs, tags)                etcd, health, kubeconfig)     FluxInstance -> clusters/<name>)
```

The manager only *builds* clusters. Each workload cluster then runs its own Flux against
`clusters/<name>/` exactly as today, so a manager outage never takes a workload cluster down.

### The custom resource

One XRD, `TalosCluster` (group e.g. `platform.ellin.net`). Sketch:

```yaml
apiVersion: platform.ellin.net/v1alpha1
kind: TalosCluster
metadata: {name: dev1}
spec:
  talosVersion: v1.14.5
  kubernetesVersion: v1.37.1
  proxmox:
    node: pve                  # default placement; per-pool override allowed
    storage: local-lvm
  network:
    vlan: 10                   # always 10 for new clusters (CLAUDE.md)
    gateway: 192.168.10.1
    controlPlaneIP: 192.168.10.56
    workerIPs: [192.168.10.57, 192.168.10.58]   # length == worker count
  controlPlane: {cpu: 4, memoryMiB: 8192, diskGiB: 40}
  workers: {count: 2, cpu: 4, memoryMiB: 8192, diskGiB: 60}
  loadBalancer: {range: 192.168.11.10-192.168.11.20}
  platform: {clusterName: dev1}   # key in clusters.yaml (phase 1); apps inline later
```

Derived by the composition, not typed by the user:

- VM ID from IP (`192.168.10.56` -> `10056`) -- the repo's existing rule.
- `allowSchedulingOnControlPlanes = (workers.count == 0)` in the Talos config patch.
- `metallb_ignore_exclude_lb = (workers.count == 0)` passed to the platform layer (see R2/Platform).
- Proxmox tags, so the Ansible dynamic inventory keeps working.

Validation in the XRD (CEL): `len(workerIPs) == workers.count`; IPs outside the DHCP range
`192.168.8.16-192.168.10.50`; `workers.count >= 0`.

## Layers in detail

### 1. VM layer (clone of template 9100)

Talos VMs are a different animal from the Ansible-managed Linux VMs: no cloud-init user setup, no SSH, no apt/Ansible
baseline. They are full clones of **template 9100** (a Talos disk image with, presumably, the qemu-guest-agent extension --
**VERIFY** what is baked in: Talos version, schematic/extensions, disk size, nocloud vs. none, SCSI controller).

Consequences:
- Talos version is whatever 9100 contains at clone time; moving versions is `talosctl upgrade` (installer image), not a re-clone. The XR's `talosVersion` drives the upgrade Job, and the *template* is refreshed separately.
- Cloning to a Proxmox node other than the one holding 9100 needs either shared storage or a copy of the template per node. The environment object (below) maps node -> template ID, so `pve2` can have its own template.
- Per-VM settings to apply after clone: name, VM ID (derived), cores/memory/disk resize, NIC on `vmbr1` with VLAN tag 10, tags (so Ansible's dynamic inventory ignores or classifies them), start on boot. No IP at clone time: the static IP is delivered in the Talos machine config (apply over the maintenance API on the DHCP lease, or nocloud if 9100 is set up for it -- **VERIFY**).

Mechanism options (no linux-vm module):

| Option | Notes |
|---|---|
| A. New small purpose-built Terraform module (`talos-vm`: clone 9100, resize, NIC, tags) run via provider-terraform | Reuses bpg/proxmox knowledge; state per cluster |
| B. Upjet-generated Proxmox provider | **VERIFY** it exists/is maintained |
| C. Job in the bootstrapper image calling the Proxmox API (`qm clone` equivalent) | Idempotent script, no extra state, we own it; fits the "custom init-container image" idea you already have |

Leaning **C** now that the module is out: clone + resize + tag is ~5 API calls, and the same image already needs
Proxmox-agnostic logic. Revisit A if drift detection matters.

### 2. Talos layer (init-container image)

A custom image, `talos-bootstrapper` (talosctl, kubectl, jq/yq, sops, age, flux CLI). Run as a Job per
phase, or as init containers of one Job, all **idempotent** (safe to re-run on every reconcile):

1. `gen-secrets`: if Secret `<name>-talos-secrets` is absent, `talosctl gen secrets`, store it in the manager. **Also back it up to 1Password** -- losing this bundle means losing the ability to administer the cluster.
2. `gen-config`: `talosctl gen config` with patches (installer image, qemu-guest-agent ext, network, `allowSchedulingOnControlPlanes`, node labels, optional VIP).
3. `apply`: wait for the maintenance API on each node (port 50000, `--insecure`), apply control-plane then worker configs.
4. `bootstrap`: `talosctl bootstrap` exactly once (guard with an annotation/ConfigMap), then wait for `talosctl health`.
5. `kubeconfig`: write `<name>-kubeconfig` Secret in the manager (this is also what the Crossplane Kubernetes/Helm providers consume).

Manager must be able to reach node IPs on 50000 and 6443 (VLAN 10 from the current LAN/VLAN -- **VERIFY** routing; `talos-test` is on 192.168.1.0/24).

### 3. Platform layer (R1 lives here)

Do not fork the bootstrap logic. Put `bootstrap/bootstrap.sh` into the bootstrapper image and have the final Job
call it with the new cluster's kubeconfig. One code path means the manual and Crossplane routes cannot drift.

**Age key (D1):** the Job generates the cluster's age key (`age-keygen`), stores the private key in a Secret on the manager
(`<name>-age`), installs it in the new cluster as `flux-system/sops-age` (what `bootstrap.sh` does with the key file today), and
publishes the **public** key in the XR status. For the legacy path nothing changes (`new-cluster.sh` writes
`~/.config/sops/age/<name>.agekey` and `keys/<name>.pub`).

**The one remaining gap:** secrets in `clusters/<name>/secrets/` are encrypted to `admin + cluster` public keys and committed. If
the key is created only at bootstrap, the commit that creates the cluster cannot already contain secrets encrypted to it. Ways out:

- **P1 -- manager supplies secrets (recommended):** the Job, which has the admin material, creates the AWS-credential Secrets directly in the new cluster from values held on the manager (1Password -> External Secrets, or a plain Secret). Apps then don't need SOPS secrets for these. Legacy clusters keep SOPS.
- **P2 -- shared "manager-built" age key:** one age key pair for all Crossplane-built clusters, public key committed in `keys/`, private key on the manager. Secrets can be encrypted ahead of time and the commit is complete. Cost: a leaked key opens every such cluster's secrets.
- **P3 -- pre-generate the key** (`new-cluster.sh` before the commit) and reference it from the XR. Zero new design, but it is a manual step before the commit, and the key is not "created by bootstrap".
- P4 -- two commits (create, then add secrets). Rejected.

P1 matches your intent best (bootstrap creates and owns the key, manager stores it) while keeping the single commit.

MetalLB (R2): reuse the `metallb_ignore_exclude_lb` option added in commit f9844a3. The composition computes it from `workers.count`
and the platform layer must feed it to the right cluster's app options. Today options live in `clusters.yaml`, so for phase 1
the single commit includes a `clusters.yaml` entry (hand-written or produced by a generator).

Medium term: make `TalosCluster.spec.platform.apps` the source, and generate `clusters/<name>/` from the XR in CI
(`render.py` already does exactly this from `clusters.yaml`). Then `clusters.yaml` shrinks to legacy clusters.

## Proxmox environment (where host settings live)

Cluster specs should not repeat endpoint, credentials, node names, storage pools, bridge or template IDs. Proposal: a
cluster-scoped **`ProxmoxEnvironment`** (a small CRD, or a Crossplane `EnvironmentConfig` that the composition function reads; the
`EnvironmentConfig` route needs no new CRD -- **VERIFY** fit with the Crossplane version) named per Proxmox cluster, e.g. `homelab`:

```yaml
apiVersion: platform.ellin.net/v1alpha1
kind: ProxmoxEnvironment
metadata: {name: homelab}
spec:
  endpoint: https://192.168.8.2:8006/api2/json
  credentialsSecretRef: {namespace: crossplane-system, name: proxmox-api}   # API token, never inline
  insecureTLS: false
  network: {bridge: vmbr1, vlan: 10, gateway: 192.168.10.1}
  nodes:
    pve:  {storage: local-lvm, templateVmId: 9100}
    pve2: {storage: local-lvm, templateVmId: 9100}   # needs its own template or shared storage
  defaults: {node: pve, tags: [talos, k8s]}
```

A `TalosCluster` then only says `spec.proxmoxRef: homelab` and, optionally, overrides: `controlPlane.node`, `workers.nodes: [...]`
(or `placement: spread`), `storage`. Resolution order: field on the cluster > environment node entry > environment default.
This also keeps the "legacy" Proxmox facts (two physical nodes, VLAN 10) in one reviewable file, and a second Proxmox site
would be another environment object rather than a schema change.

## What "one commit" contains

Phase 1 (realistic): XR file in `management/clusters/dev1.yaml` + `clusters.yaml` entry + regenerated `clusters/dev1/` +
`VLAN10-IP-ALLOCATION.md` rows (done **before** the XR, D2: the XR just consumes the reserved IPs). A
`hack/new-talos-cluster.sh <name> --workers N` can scaffold all four.
Phase 3 (goal): XR file + allocation rows only. A CI allocation check is now optional (a consistency lint), not a safety gate.

## Scaling and day-2

- **Add workers (0 -> N, N -> N+1):** new IP in `workerIPs`, clone, Job applies worker config. Going 0 -> N additionally flips `allowSchedulingOnControlPlanes` to false and `ignoreExcludeLB` to false. Existing pods on the control plane are not evicted automatically; the Job should cordon-and-drain the control plane or the doc must say to.
- **N -> 0 is forbidden (D3).** Enforce in the XRD with a CEL transition rule, roughly:
  `x-kubernetes-validations: [{rule: "oldSelf.workers.count == 0 || self.workers.count > 0", message: "cannot scale workers to 0"}]`.
  (**VERIFY** transition rules are supported on the XRD schema in the installed Crossplane; otherwise a validating function in the pipeline.) To reach 0 you rebuild the cluster. Also keeps the local-path volume-pinning problem out of scope.
- **N -> M, M > 0:** cordon/drain, `talosctl reset`, `kubectl delete node`, then delete VM. Never delete the VM first.
- **Upgrades:** `talosVersion`/`kubernetesVersion` changes trigger `talosctl upgrade` / `upgrade-k8s` Jobs, one node at a time, control plane first.
- **Deletion:** default Crossplane `deletionPolicy` for the VM resources should be safe; consider a finalizer-protected annotation (`platform.ellin.net/allow-delete: "true"`) so a bad revert can't destroy a cluster.
- **Status:** XR conditions `VMsReady`, `TalosReady`, `KubernetesReady`, `PlatformReady`; kubeconfig Secret name in status.

## Crossplane choices (VERIFY versions)

- Use **composition functions in pipeline mode** (function-go-templating or function-kcl) -- classic patch-and-transform is deprecated direction. I believe Crossplane v2 also makes XRs namespaced and drops claims; confirm the installed version's model before writing the XRD.
- Install Crossplane + functions + providers as new apps in this repo (`apps/crossplane`, `apps/crossplane-config`) enabled for `talos-test` in `clusters.yaml`, so the manager itself is built by the existing platform. The XRD/Composition/XRs live in e.g. `management/` and are synced by a second Flux Kustomization on the manager only.
- Providers likely needed: provider-terraform (or opentofu) / Proxmox provider, provider-kubernetes (for resources inside the new cluster), provider-helm (optional).

## Alternative worth a fair look: Cluster API

CAPI with the Proxmox infra provider (CAPMOX) and Talos bootstrap/control-plane providers (CABPT/CACPPT) already models
"1 CP + N workers", scaling, rolling upgrades and node lifecycle, which are the hardest parts of this plan. **VERIFY** current
maturity of CAPMOX. Crossplane's advantages are one tool for everything and reusing the Terraform standards. A hybrid
(Crossplane XRD as the friendly API, composing CAPI `Cluster` objects) is possible but adds a layer. Worth deciding before building.

## Risks

- Manager is a SPOF for *changes* (not for running clusters). It is also single-node with etcd on one VM: back up Talos secrets and the manager's etcd; the manager must be rebuildable via the legacy path (R1).
- Terraform state inside the cluster (option A) must be backed up too.
- Talos secrets bundle loss = unrecoverable admin access.
- IP/VM-ID collisions: allocation is done by hand before creating the XR (D2); a CI lint against the markdown tables is nice-to-have.
- Template 9100 drift: it is undocumented in the repo, and a template change silently changes new clusters. Record how it is built (and its Talos version) next to this plan.

## Phased plan

0a. Make template 9100 reproducible: record its provenance (Image Factory schematic ID/extensions, Talos version, disk/SCSI/BIOS/machine settings from `qm config 9100` and `qm config 155`) and script its creation (`hack/` or the bootstrapper image) so it can be rebuilt per Proxmox node and per Talos version.
0. Decide Crossplane-vs-CAPI and the Proxmox provider (spike, half a day each).
1. Install Crossplane + functions + providers on `talos-test` via `apps/`.
2. Build and publish `talos-bootstrapper` image (include `bootstrap.sh`); test it by hand against a throwaway VM.
3. XRD + composition for VM layer only; create/destroy a 1-node cluster's VMs.
4. Add Talos layer; end-to-end 1 CP, 0 workers (the `allowScheduling` + `ignoreExcludeLB` case, same as talos-test).
5. Platform layer (secrets option S2); legacy `bootstrap.sh` unchanged.
6. Workers N > 0, scale up/down, upgrades.
7. Collapse `clusters.yaml` into the XR; CI allocation check.

## Open questions

1. Crossplane vs CAPI (above)? With 9100 cloning and N->0 forbidden, CAPI's advantages shrink somewhat but scaling/upgrades remain the draw.
2. VM mechanism: Job calling the Proxmox API (C, leaning) vs a small `talos-vm` Terraform module (A)?
3. Secrets: P1 (manager supplies), P2 (shared key), or P3 (pre-generated key)?
4. What exactly is in template 9100 (Talos version, extensions, nocloud?) and does `pve2` have it or shared storage? ProxmoxEnvironment as new CRD or `EnvironmentConfig`? Spread CP/workers across nodes?
5. Can the manager (192.168.1.0/24) reach VLAN 10 node IPs on 50000/6443, and can Talos nodes reach GitHub/registries?
6. Is a control-plane VIP needed later (HA = more CPs)? The spec says 1 CP; keep a path to 3 open?
7. Where should the bootstrapper image live (ghcr.io/jeffellin, Gitea registry) and how is it built (Gitea Actions / GitHub Actions)?
