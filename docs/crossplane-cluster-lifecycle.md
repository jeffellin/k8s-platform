# Crossplane-managed cluster lifecycle (brainstorm / plan)

Status: **idea, no code**. Nothing here is verified against the live cluster; items marked
**VERIFY** are things I believe but have not checked.

## Decisions so far (rev 2)

- **D1** The per-cluster age key is generated by the bootstrap step and stored on the manager (Secret). See Platform layer for the one remaining gap (secrets encrypted before the key exists).
- **D2** IPs and VM IDs are allocated **before** the `TalosCluster` is created (allocation docs updated by hand/script in the same commit). The composition never allocates; it only derives VM ID from IP.
- **D3** Worker count may go **0 -> N** but **never N -> 0** (enforced in the XRD, see Scaling).
- **D4** Talos VMs are **not** built with `terraform/modules/linux-vm`. They are cloned from Proxmox template **9100**. (Template 9100 was built by hand following `docs/SingleNodeKubernetesonProxmox.md`; the `talos-01` VM was cloned from it and configured manually per `docs/TalosHandoff.md`. Those two docs are the source of truth for the manual procedure this plan automates. Scripting the template build is phase 0a.)
- **D5** Proxmox host settings (cluster node, storage pool, bridge, template) live in a separate, reusable environment object, not in each cluster. See "Proxmox environment".

- **D6** **Crossplane v2 is the chosen approach** (spike result below). Jeff has contacts on the Upjet side, so if the Job-based VM layer proves awkward, a proper Upjet-generated Proxmox provider is an available fallback rather than a dependency.

- **D7** Secrets use **P1**: bootstrap creates the per-cluster age key and stores it on the manager; the AWS credentials are held on the manager and written into the new cluster by the bootstrap Job (no SOPS files needed for them). For now the credentials live in a **plain Secret on the manager**, seeded from 1Password by `hack/seed-secrets.sh`; External Secrets can replace it later without changing the Job.

## Goal

Add a new Kubernetes cluster with **one commit**:

1. VMs are created to the homelab standards (VLAN 10, IP/VM-ID rules, cloud-init/guest-agent, tags).
2. Talos is installed and bootstrapped.
3. The platform layer (Flux Operator + this repo's apps) comes up on it.

Hard requirements:

- **R1** The existing path (`hack/new-cluster.sh` -> `render.py` -> `bootstrap/bootstrap.sh`) keeps working,
  for clusters not built by Crossplane (kubeadm, hand-built Talos, the manager itself).
- **R2** Topology is `1 control plane + N workers`, `N >= 0`.
  - `N > 0`: normal scheduling (control plane tainted, MetalLB excludes it).
  - `N == 0`: workloads allowed on the control plane **and** MetalLB must announce from it.
- **R3** The existing `talos-test` cluster acts as the **manager** (runs Crossplane).

## Architecture

```
git commit ──> manager Flux ──> TalosCluster (XR) ──> Composition (pipeline)
                                   │
        ┌──────────────────────────┼──────────────────────────────┐
        ▼                          ▼                              ▼
   VM layer                   Talos layer                  Platform layer
 (Proxmox VMs from         (secrets bundle, machine      (kubeconfig -> bootstrap.sh
  Talos image, IPs,         configs, apply, bootstrap     logic: Flux Operator, age key,
  IDs, tags)                etcd, health, kubeconfig)     FluxInstance -> clusters/<name>)
```

The manager only *builds* clusters. Each workload cluster then runs its own Flux against
`clusters/<name>/` exactly as today, so a manager outage never takes a workload cluster down.

### The custom resource

One XRD, `TalosCluster` (group e.g. `platform.ellin.net`). Sketch:

```yaml
apiVersion: platform.ellin.net/v1alpha1
kind: TalosCluster
metadata: {name: dev1}
spec:
  talosVersion: v1.14.5
  kubernetesVersion: v1.37.1
  proxmox:
    node: pve                  # default placement; per-pool override allowed
    storage: local-lvm
  network:
    vlan: 10                   # always 10 for new clusters (CLAUDE.md)
    gateway: 192.168.10.1
    controlPlaneIP: 192.168.10.56
    workerIPs: [192.168.10.57, 192.168.10.58]   # length == worker count
  controlPlane: {cpu: 4, memoryMiB: 8192, diskGiB: 40}
  workers: {count: 2, cpu: 4, memoryMiB: 8192, diskGiB: 60}
  loadBalancer: {range: 192.168.11.10-192.168.11.20}
  platform: {clusterName: dev1}   # key in clusters.yaml (phase 1); apps inline later
```

Derived by the composition, not typed by the user:

- VM ID from IP (`192.168.10.56` -> `10056`) -- the repo's existing rule.
- Control-plane scheduling: with `workers.count == 0` the `NoSchedule` taint is removed from the generated `KubeNodeConfig` (Talos 1.14 -- see Talos layer; `allowSchedulingOnControlPlanes` is rejected in 1.14).
- `metallb_ignore_exclude_lb = (workers.count == 0)` passed to the platform layer (see R2/Platform).
- Proxmox tags, so the Ansible dynamic inventory keeps working.

Validation in the XRD (CEL): `len(workerIPs) == workers.count`; IPs outside the DHCP range
`192.168.8.16-192.168.10.50`; `workers.count >= 0`.

## Layers in detail

### 1. VM layer (clone of template 9100, nocloud)

Source of truth: `docs/SingleNodeKubernetesonProxmox.md` Step 2. Template **9100** (`talos-v1.14.5`) is:

- Talos **v1.14.5**, Image Factory **nocloud** `nocloud-amd64.raw`, schematic `88d1f7a5...6040b`
  with extensions `qemu-guest-agent`, `iscsi-tools`, `util-linux-tools`.
- `--machine q35 --cpu host --cores 4 --memory 8192 --balloon 0 --scsihw virtio-scsi-single --agent enabled=1`,
  SeaBIOS, `scsi0` 64G (`discard=on,ssd=1`), `ide2` = cloud-init drive, `net0 virtio,bridge=vmbr0` (**note: vmbr0, not VLAN 10**).
- Hand-built on the Proxmox host (`192.168.1.52`) with `qm create ... import-from=` (needs a root shell; API tokens generally can't do `import-from` -- **VERIFY**).

Because it is **nocloud**, the IP is set at clone time through the Proxmox cloud-init drive; the node boots straight into Talos
maintenance mode **at its final static IP** (no DHCP discovery, no guest-agent lookups). Per-VM clone recipe (what `talos-01` got by hand):

```
qm clone 9100 <vmid> --name <node-name> --full --target <pve-node> --storage <pool>
qm set   <vmid> --net0 virtio,bridge=vmbr1,tag=10          # template is vmbr0; new clusters go on VLAN 10
qm set   <vmid> --ipconfig0 ip=<ip>/22,gw=192.168.10.1 --nameserver <dns> --searchdomain ellin.net
qm set   <vmid> --cores <n> --memory <mib> --tags talos,<cluster>
qm resize <vmid> scsi0 <size>
qm set   <vmid> --scsi1 <pool>:<gib>,discard=on,ssd=1       # data disk for UserVolumeConfig (see below)
qm start <vmid>
```

Notes:
- **VM name = hostname** (cloud-init), so name VMs `<cluster>-cp-1`, `<cluster>-w-1`..., and keep cluster names unique (the manager's own cluster is already named `homelab`; kubeconfig context collisions otherwise).
- **Data disk:** the repo's `local-path-provisioner` app expects `/var/mnt/local-path-provisioner`, which exists only if a second disk plus a `UserVolumeConfig` named `local-path-provisioner` is present. So `dataDiskGiB` is part of the spec (default 50, as on `talos-01`); omit it only for clusters that don't enable that app.
- **Template per Talos version/node:** the guide builds a new template (e.g. 9101) per Talos version for *new* nodes; existing nodes upgrade in place. So the environment object maps `(proxmox node, talosVersion) -> templateVmId`, and a template must exist on (or be reachable from) each target node.
- **Zero-touch option** (guide, Step 3): machine config can be delivered as cloud-init user-data via a `cicustom` snippet, skipping `apply-config`. It contains the cluster secrets and requires snippet files on the Proxmox host (SSH/`scp`, not the REST API -- **VERIFY**). Default to `apply-config --insecure` over the network; consider snippets later.
- Proxmox API token needs roughly `VM.Clone`, `VM.Config.*`, `VM.PowerMgmt`, `VM.Allocate`, `Datastore.AllocateSpace`, `SDN.Use` on `vmbr1` -- **VERIFY** exact set.
- Proxmox hosts have two NICs: one on 192.168.1.x (vmbr0) and one on 192.168.8.x / VLAN 10 (vmbr1), e.g. `pve` = `192.168.1.52` and `192.168.8.2`. Either address reaches the API; the environment object picks one (default the 1.x address, which the manager is on).

Mechanism options (no linux-vm module): the clone recipe is a handful of Proxmox API calls, so I still lean to **a Job in the bootstrapper image** (idempotent: skip if VM ID exists). A small Terraform module via provider-terraform or an Upjet provider remain alternatives.

### 2. Talos layer (init-container image)

Source of truth: `docs/TalosHandoff.md` and Guide Steps 3-4. A custom image, `talos-bootstrapper` (talosctl **v1.14.x matching the cluster**, kubectl,
jq/yq, sops, age, flux CLI, `bootstrap.sh`). Run as a Job, or init containers of one Job, all **idempotent**:

1. `gen-secrets`: if Secret `<name>-talos-secrets` is absent, `talosctl gen secrets -o secrets.yaml` and store it in the manager. **Also back it up to 1Password.** The handoff doc's open item stands: the existing `secrets.yaml` for the `homelab` cluster lives only in `~/talos` on `homelab-3-vm-01` and a Mac copy.
2. `gen-config`: `talosctl gen config <name> https://<cpIP>:6443 --with-secrets ... --config-patch @patch.yaml`. The patch is the **Talos 1.14 multi-document** form (pre-1.14 `machine.install` / `machine.kubelet` / `cluster.allowSchedulingOnControlPlanes` are rejected):
   - `UnattendedInstallConfig` with the nocloud installer image `factory.talos.dev/nocloud-installer/<schematic>:<talosVersion>` and `diskSelector: disk.dev_path == "/dev/sda"`.
   - `UserVolumeConfig` named `local-path-provisioner` on `!system_disk`, `minSize` ~ 40GB, when `dataDiskGiB` is set.
   - No network config: IP/DNS/hostname come from the cloud-init drive, so **the same `controlplane.yaml` / `worker.yaml` applies to every node**.
3. `taint`: when `workers.count == 0`, delete the control-plane `NoSchedule` taint from the `KubeNodeConfig` document in `controlplane.yaml` (the handoff does this by hand with `vi` and notes it is lost on every regeneration). Scripted with `yq` in the Job so it is applied every time. **VERIFY** whether a `$patch: delete`/JSON patch can do it inside `--config-patch` instead.
4. `apply`: wait for port 50000 on each node, `talosctl apply-config --insecure -n <ip> --file ...` (control plane first, then workers). 1.14 has no reboot mode: the Job must `talosctl reboot` itself when a change needs it.
5. `bootstrap`: `talosctl bootstrap` **exactly once** (guard with an annotation on the XR/ConfigMap), then `talosctl health`.
6. `kubeconfig`: write `<name>-kubeconfig` and `<name>-talosconfig` Secrets in the manager (also what provider-kubernetes/helm consume).

The manual talosctl runs happened from `homelab-3-vm-01` (Ubuntu, VLAN 10 side) because the Mac was blocked by macOS Local Network privacy. The Job pod needs the same
reach: **manager pod -> node IP on 50000 and 6443**. `talos-test` is on 192.168.1.0/24; new clusters are on VLAN 10. Assumption (confirmed): all VLANs/subnets can route to each other, so no extra network work is needed; still smoke-test `nc -zv <vlan10-ip> 50000` from a manager pod before building the Job.

### 3. Platform layer (R1 lives here)

Do not fork the bootstrap logic. Put `bootstrap/bootstrap.sh` into the bootstrapper image and have the final Job
call it with the new cluster's kubeconfig. One code path means the manual and Crossplane routes cannot drift.

**Age key (D1):** the Job generates the cluster's age key (`age-keygen`), stores the private key in a Secret on the manager
(`<name>-age`), installs it in the new cluster as `flux-system/sops-age` (what `bootstrap.sh` does with the key file today), and
publishes the **public** key in the XR status. For the legacy path nothing changes (`new-cluster.sh` writes
`~/.config/sops/age/<name>.agekey` and `keys/<name>.pub`).

**The one remaining gap:** secrets in `clusters/<name>/secrets/` are encrypted to `admin + cluster` public keys and committed. If
the key is created only at bootstrap, the commit that creates the cluster cannot already contain secrets encrypted to it. Ways out:

- **P1 -- manager supplies secrets (DECIDED, D7):** the Job, which has the admin material, creates the AWS-credential Secrets directly in the new cluster from values held on the manager (1Password -> External Secrets, or a plain Secret). Apps then don't need SOPS secrets for these. Legacy clusters keep SOPS.
- **P2 -- shared "manager-built" age key:** one age key pair for all Crossplane-built clusters, public key committed in `keys/`, private key on the manager. Secrets can be encrypted ahead of time and the commit is complete. Cost: a leaked key opens every such cluster's secrets.
- **P3 -- pre-generate the key** (`new-cluster.sh` before the commit) and reference it from the XR. Zero new design, but it is a manual step before the commit, and the key is not "created by bootstrap".
- P4 -- two commits (create, then add secrets). Rejected.

P1 matches your intent best (bootstrap creates and owns the key, manager stores it) while keeping the single commit.

MetalLB (R2): reuse the `metallb_ignore_exclude_lb` option added in commit f9844a3. The composition computes it from `workers.count`
and the platform layer must feed it to the right cluster's app options. Today options live in `clusters.yaml`, so for phase 1
the single commit includes a `clusters.yaml` entry (hand-written or produced by a generator).

Medium term: make `TalosCluster.spec.platform.apps` the source, and generate `clusters/<name>/` from the XR in CI
(`render.py` already does exactly this from `clusters.yaml`). Then `clusters.yaml` shrinks to legacy clusters.

## Proxmox environment (where host settings live)

Cluster specs should not repeat endpoint, credentials, node names, storage pools, bridge or template IDs. Proposal: a
cluster-scoped **`ProxmoxEnvironment`** (a small CRD, or a Crossplane `EnvironmentConfig` that the composition function reads; the
`EnvironmentConfig` route needs no new CRD -- **VERIFY** fit with the Crossplane version) named per Proxmox cluster, e.g. `homelab`:

```yaml
apiVersion: platform.ellin.net/v1alpha1
kind: ProxmoxEnvironment
metadata: {name: homelab}
spec:
  endpoint: https://192.168.1.52:8006/api2/json      # pve has a second NIC at 192.168.8.2 (VLAN 10); either works
  credentialsSecretRef: {namespace: crossplane-system, name: proxmox-api}   # API token, never inline
  insecureTLS: false
  network: {bridge: vmbr1, vlan: 10, gateway: 192.168.10.1}
  nodes:
    pve:
      storage: local-lvm
      templates: {v1.14.5: 9100}      # (talosVersion -> template VM ID); 9101 etc. added per release
    pve2:
      storage: local-lvm
      templates: {}                   # none yet: needs its own template or shared storage
  defaults: {node: pve, tags: [talos, k8s]}
```

A `TalosCluster` then only says `spec.proxmoxRef: homelab` and, optionally, overrides: `controlPlane.node`, `workers.nodes: [...]`
(or `placement: spread`), `storage`. Resolution order: field on the cluster > environment node entry > environment default.
This also keeps the "legacy" Proxmox facts (two physical nodes, VLAN 10) in one reviewable file, and a second Proxmox site
would be another environment object rather than a schema change.

## What "one commit" contains

Phase 1 (realistic): XR file in `management/clusters/dev1.yaml` + `clusters.yaml` entry + regenerated `clusters/dev1/` +
`VLAN10-IP-ALLOCATION.md` rows (done **before** the XR, D2: the XR just consumes the reserved IPs). A
`hack/new-talos-cluster.sh <name> --workers N` can scaffold all four.
Phase 3 (goal): XR file + allocation rows only. A CI allocation check is now optional (a consistency lint), not a safety gate.

## Scaling and day-2

- **Add workers (0 -> N, N -> N+1):** new IP in `workerIPs`, clone, Job applies worker config. Going 0 -> N additionally flips `allowSchedulingOnControlPlanes` to false and `ignoreExcludeLB` to false. Because there is no `apply-config` reboot mode, re-adding the taint means regenerating `controlplane.yaml` without the `yq` step, applying it (and rebooting if needed), then `kubectl drain` the control plane so pods move to the workers.
- **N -> 0 is forbidden (D3).** Enforce in the XRD with a CEL transition rule, roughly:
  `x-kubernetes-validations: [{rule: "oldSelf.workers.count == 0 || self.workers.count > 0", message: "cannot scale workers to 0"}]`.
  (**VERIFY** transition rules are supported on the XRD schema in the installed Crossplane; otherwise a validating function in the pipeline.) To reach 0 you rebuild the cluster. Also keeps the local-path volume-pinning problem out of scope.
- **N -> M, M > 0:** cordon/drain, `talosctl reset`, `kubectl delete node`, then delete VM. Never delete the VM first.
- **Upgrades:** `talosVersion`/`kubernetesVersion` changes trigger `talosctl upgrade` / `upgrade-k8s` Jobs, one node at a time, control plane first.
- **Deletion:** default Crossplane `deletionPolicy` for the VM resources should be safe; consider a finalizer-protected annotation (`platform.ellin.net/allow-delete: "true"`) so a bad revert can't destroy a cluster.
- **Status:** XR conditions `VMsReady`, `TalosReady`, `KubernetesReady`, `PlatformReady`; kubeconfig Secret name in status.

## Crossplane choices (VERIFY versions)

- Use **composition functions in pipeline mode** (function-go-templating or function-kcl) -- classic patch-and-transform is deprecated direction. I believe Crossplane v2 also makes XRs namespaced and drops claims; confirm the installed version's model before writing the XRD.
- Install Crossplane + functions + providers as new apps in this repo (`apps/crossplane`, `apps/crossplane-config`) enabled for `talos-test` in `clusters.yaml`, so the manager itself is built by the existing platform. The XRD/Composition/XRs live in e.g. `management/` and are synced by a second Flux Kustomization on the manager only.
- Providers likely needed: provider-terraform (or opentofu) / Proxmox provider, provider-kubernetes (for resources inside the new cluster), provider-helm (optional).

## Spike result: Crossplane vs Cluster API (web research, 2026-11-08)

Based on search results only (secondary sources in places); nothing was installed or tested.

**Cluster API route (CAPMOX + Talos providers)**
- CAPMOX (`ionos-cloud/cluster-api-provider-proxmox`) is actively released: v0.8 introduced the `v1alpha2` API (works with CAPI v1.11 / contract `v1beta2`), v0.9.0 is the newest I saw. The v0.1-v0.7 line is `v1alpha1` and marked obsolete, so it is still moving fast and had breaking API changes recently.
- Talos bootstrap provider (CABPT) generates machine configs; the Talos **control plane provider (CACPPT) states that Sidero Labs is no longer actively developing it** and points to Omni. For a design that needs 1 CP + N workers on Talos, losing the maintained CP provider is the biggest strike against this route (CAPI's kubeadm control plane provider doesn't apply to Talos).
- CAPI also needs its own management stack (clusterctl or the CAPI operator, cert-manager, per-provider controllers) and a different mental model (`Cluster`, `MachineDeployment`, `ProxmoxMachineTemplate`, `TalosConfigTemplate`...), plus the 1.14-style multi-document config and the template-9100/nocloud workflow would need to be expressed through CAPMOX clone settings and CABPT patches -- **unverified** whether that works with Talos 1.14's `UnattendedInstallConfig`.

**Crossplane route**
- Crossplane v2 (docs up to v2.3 exist): XRDs default to `scope: Namespaced`, **claims are gone** for new XRs, and native patch-and-transform is deprecated in favour of composition functions. So the plan's `TalosCluster` is a namespaced XR (e.g. in a `clusters` namespace); no `Claim` kind. v2 also has no built-in connection secrets for namespaced XRs: the function must emit the kubeconfig Secret explicitly. The existing wording in "Crossplane choices" should be read with this.
- Proxmox: no official provider found. A community Upjet-generated one wraps bpg/terraform-provider-proxmox (`valkiriaaquatica/provider-proxmox-bpg`, Apache-2.0, ~17 stars, ~10 open issues, says it supports Crossplane v2) and another older one (`dcoppa/provider-proxmox`). Neither has a track record I could confirm. That reinforces choosing **bootstrapper Jobs calling the Proxmox API** for the VM layer rather than depending on a small community provider.
- CEL transition rules (`oldSelf`) are standard CRD validation and XRDs generate CRDs, so the N->0 guard should work; **not confirmed in docs**, test it in phase 3.

**Comparison for this homelab**

| | Crossplane + Jobs | Cluster API (CAPMOX + CABPT/CACPPT) |
|---|---|---|
| Talos CP provider maintained | n/a (we run `talosctl`) | **No** (CACPPT unmaintained) |
| Proxmox provider | Our Job (small, owned) | CAPMOX, active, but fast-moving API |
| Scaling/upgrade logic | We write it (drain/reset, upgrade Jobs) | Provided (for kubeadm); for Talos depends on unmaintained CP provider |
| Fits template 9100 / nocloud / 1.14 multi-doc | Directly (mirrors the manual procedure) | Unverified |
| One-commit UX | One XR | `Cluster` + several templates (could be wrapped by Crossplane) |
| Extra components | Crossplane + functions | CAPI core + 3 providers + cert-manager |

**Recommendation: Crossplane v2 with composition functions plus a custom `talos-bootstrapper` image (Jobs).** CAPI's main
advantage (lifecycle logic) is weakened by the unmaintained Talos control-plane provider, and your needs are small
(1 CP, N workers, N->0 forbidden, in-place upgrades via `talosctl`). Cost: we own the scale-up/down and upgrade Jobs. Revisit CAPI
only if you later want HA control planes with automated rolling replacement.

## Risks

- Manager is a SPOF for *changes* (not for running clusters). It is also single-node with etcd on one VM: back up Talos secrets and the manager's etcd; the manager must be rebuildable via the legacy path (R1).
- Terraform state inside the cluster (option A) must be backed up too.
- Talos secrets bundle loss = unrecoverable admin access.
- IP/VM-ID collisions: allocation is done by hand before creating the XR (D2); a CI lint against the markdown tables is nice-to-have.
- Template drift: 9100 is hand-built; a new template number per Talos version is the guide's convention. The environment's `(node, talosVersion) -> template` map keeps that explicit; never edit a template in place.
- `secrets.yaml` and a first etcd snapshot for the existing `homelab` cluster are now backed up. Keep it that way: the manager must not become the sole holder of other clusters' secrets before it is itself backed up.
