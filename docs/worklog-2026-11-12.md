**Goal:** finish the Longhorn deployment testing interrupted by a session crash (cluster scale-down), and decide where Longhorn's data should live.

## Done

The scale-down had completed, but the 2-replica `lhdrain` volume was left degraded: the replica on the removed worker was lost, and Longhorn cannot place a second replica on one node (`ReplicaSchedulingFailure: precheck new replica failed: disks are unavailable`). The stale `demo2-w-2` Longhorn node object stayed behind.
- **Documented scaling down below a volume's replica count** in `docs/talos-cluster-runbook.md` (PR #43): find affected volumes, lower replicas, evict the node, scale down, delete the stale node.
- **Renamed the data user volume to `longhorn`** in `hack/talos-gen-config.sh` (PR #44), so new workers mount the 50 GB disk at `/var/mnt/longhorn`, Longhorn's default path. `ellinj/talos-automation:dev` rebuilt from `main`.

- **Scaled `demo3` from 2 workers to 1** with the runbook steps. The scale-down Job drained, reset and purged `demo3-w-2`; the volume stayed `healthy` and `attached`, the pod kept running, and the removed worker's Longhorn node object disappeared on its own.
- Results are in `docs/longhorn.md` ("Trial results (`demo3`)") and the runbook (scale-down section, plus three new Troubleshooting rows).

## Findings

- A live `kubectl annotate` of `platform.ellin.net/teardown` is reverted by Flux, because the XR file in Git has no annotation. The teardown annotation must be in the XR file in Git (quoted `"true"`). This is how `demo2` ended up rebuilding.
- One unhealthy cluster (for example `demo2` stuck in `PlatformApplying`) blocks the `talos-clusters` Kustomization health check for every cluster, so new XRs and scale-downs in Git are not applied until it clears or times out (10 minutes).
- Fresh clusters hit stalled HelmReleases: `cert-manager`, `metallb` and `external-dns` failed their first install (pods became Ready after the timeout) and Flux did not retry (`RetriesExceeded: Failed to install after 1 attempt`). `external-dns` crash-looped on the missing Contour `httpproxies` CRD. `longhorn` went into uninstall remediation, which its uninstall guard (`deletingConfirmationFlag`) refused. Annotating the HelmReleases with `reconcile.fluxcd.io/resetAt` recovered them. This is backlog F20.
- Variant A and B use the same path (`/var/mnt/longhorn`). If the user volume fails to mount, Longhorn silently uses a directory on `/var`. Verify the mount after a build (`talosctl get volumestatus u-longhorn`, or a Longhorn disk of about 49 GiB).
- `hack/scale-down-check.sh` warns that Longhorn instance-manager PodDisruptionBudgets allow 0 disruptions (the drain would block, exit 4). The warning clears once the node has no replicas.

## Next: F20 (platform bring-up resilience on slow storage)

Slow image pulls make the install time out, Flux stalls without retrying, and the `platform` Job fails and leaves the XR in `PlatformApplying`. Reproduced on `demo2` and `demo3`. Proposed order:

1. **HelmReleases:** `install.remediation.retries: -1` and a 15 minute `timeout` in the shared templates under `apps/*`. Check how this interacts with Longhorn's uninstall guard, which turned a failed install into a stuck uninstall.
2. **external-dns:** add `dependsOn: contour` in the ResourceSet.
3. **Platform Job:** longer deadline and `backoffLimit`; a clear `PlatformReady=False` reason on failure; retry by recreating the Job instead of waiting forever.
4. **Job logging:** print which Kustomizations or HelmReleases are not Ready, not only counts.
5. **Optional:** a pull-through registry cache or pre-pulled images; a runbook line that slow storage means slow bring-up.
6. **Verify:** build a cluster on slow storage with no manual steps; it reaches Ready.
